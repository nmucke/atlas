# Review an Atlas paper

Use when asked to assess, summarize, or critique a paper stored in Atlas.

If the user also asks to find or attach a missing PDF, follow `atlas-zotero-maintenance` first. Report any incomplete PDF action separately instead of substituting a saved abstract-only review for that request. After a successful attachment, use `atlas_index` and retrieve the new paper context before reviewing the full text. If the session lacks the PDF tools, explain that Atlas and the host's MCP connection need refreshing; do not present this as a permanent Atlas limitation.

1. Start a run with `atlas_begin_run({purpose, agentName, model})`. Identify the requested paper, then retrieve its metadata and relevant text with `atlas_get_context({runId, paperId, ...})`; use `atlas_search` for specific claims or comparisons. For either tool, follow each returned `nextOffset` until null when reviewing all available paper evidence.
2. State what material was available: metadata, abstract, full text, and/or OCR. If the PDF is unavailable, unindexed, or has no extractable text, keep the review at the metadata/abstract level and say full-text analysis was unavailable; never imply that you read the PDF or use filesystem access to retrieve it. If only title-level metadata is available, limit the response to that and ask for an abstract or full text before making a substantive assessment.
3. Separate the paper's reported claims and findings from your assessment. Cover the question, approach, evidence, contribution, limitations, and relevance to the user's stated purpose only when supported by retrieved material. Mark uncertainty explicitly.
4. Ground every paper-specific factual claim in retrieved evidence, but keep the review body and conversational summary free of raw chunk IDs, hashes, and bracketed internal references. Keep returned citation IDs only in the structured `citationIds` field when saving; Atlas displays them separately in Evidence. Use readable source names or page numbers if a specific attribution is helpful. Do not infer unreported methods, results, sample sizes, or causal conclusions.
5. Retrieve the existing Atlas tag vocabulary with `atlas_list_tags({runId, ...})`, following `nextOffset` until null. Suggest a small set of relevant tags for this paper, preferring existing names and definitions. Avoid tags already assigned to the paper and near-duplicates of existing tags. Only propose a new tag when the existing vocabulary cannot express a useful concept; include a brief description explaining its meaning and scope. Distinguish existing tags from new suggestions in your response.
6. Submit useful tag suggestions as a separate pending proposal with `atlas_submit({runId, kind: 'tags', title, body, paperId, tags: [{name, description}], citationIds})`. This proposal is part of the paper-review workflow. Cite retrieved paper evidence and explain briefly why the tags fit. Reuse existing descriptions; every new tag needs a nonempty brief description. The user must approve the proposal in Atlas before any tags are created or assigned. Never claim suggestions were approved or applied. If the user explicitly asks for a response only with nothing saved, present the suggestions without submitting them.
7. Fetch `atlas_get_profile({runId})` and use the saved interests plus the user's stated purpose to decide whether this paper is worth their reading time. Give an integer score with this scale: 1 = not recommended, 2 = low priority, 3 = worth considering, 4 = recommended, 5 = strongly recommended. Include a brief explanation (1–3 sentences) of relevance, expected value, and any evidence limits; explicitly explain low scores too. If no profile or purpose is available, say the score reflects general research value rather than a personalized judgment. Keep raw citation IDs out of the explanation. Always include this assessment in your response.
8. Retrieve `atlas_list_projects({runId, ...})`, paging through all projects, then retrieve context for plausible matches. Recommend which existing project(s) the paper fits, with a brief concrete reason for each. Do not force a match: explicitly say when no project fits or no projects exist. For each useful match not already linked, submit a separate pending `atlas_submit({runId, kind: 'recommendation', title, body: projectFitReason, paperId, projectId, level, citationIds})` with paper and project evidence. Choose `essential`, `recommended`, or `optional` for that project's relevance, independently of the overall reading score. This is part of the review workflow unless the user requests nothing saved. The Recommendations page displays these suggestions; accepting one links the paper to the project. Never claim it was linked before approval.
9. Unless the user explicitly asks for nothing saved, save the completed review and reading assessment by submitting it with `atlas_submit({runId, kind: 'review', title, body, paperId, readingRecommendation: {score, reason}, citationIds})`. Include the reading score and brief rationale on every saved review so it appears on Library → Recommendations. Reviews require 1–100 returned citation IDs in this separate field, not embedded in `body`. Keep it labeled as AI-generated review content and do not overwrite or blend it with human notes. Saving or approving a review does not approve its separate tag proposal.
